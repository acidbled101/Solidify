A · Trajectory through the fork scrub the sampler step

The latent's actual path through sampling, in a fixed 2-D random projection of the full SLat state (LatentProbe in dpo_branch.py). The basis is drawn once per run and reused for every step and every branch. Each basis vector is unit-norm, so the projection cannot invent separation: two branches close in the real ~22k-dimensional latent cannot look far apart here. The converse does not hold — two dimensions cannot guarantee that everything far apart in the full space looks far apart on screen, so branches may appear coincident while genuinely differing. Read distance here as a lower bound, not a measurement. Drag the slider to walk the run: grey is the single pre-branch trajectory, the ring marks each fork, and past it the three candidates (unperturbed reference, the random perturbation, and the gradient-steered result) diverge. Faint grey is the not-yet-reached path.

B · Velocity and latent scale per step v_θ over the schedule

RMS of the model's predicted velocity v_θ(x,t) and of the latent itself, at every sampler step of this run. v is recovered exactly rather than estimated: the Euler update is x_prev = x − (t−t_prev)·v, so dividing the increment by the timestep returns the velocity the model actually predicted. The vertical marker follows the slider above; dashed lines mark the forks. What to look for: whether the perturbation at the fork produces any visible excursion in ‖v‖ — if the three branches are indistinguishable here, the perturbation is small relative to the flow.

C · What the judge decided, per fork this run

The three candidate scores at each fork of this run, and what the gradient changed. gain (random) is what the perturbation bought before any steering; gain (steering) is what the gradient added on top. The re-rank gate means a negative steering gain costs compute, not output quality — the run resumes from the reference whenever the steered candidate fails to beat it.

D · Every run, pooled the decisive question

One run is an anecdote. This pools every branch of every real run on disk — each fork is an independent trial of the same question — and asks the one thing that settles whether the gradient earns its cost: did steering ever change which branch the judge preferred? If the flip rate stays near zero and the mean steering gain stays within noise, best-of-N sampling dominates the whole approach at lower compute. Synthetic demo traces are excluded from the aggregates (and labelled in the CSVs).

Verdict

Four claims from the brief, each tested rather than illustrated. Where the measurement contradicts the claim, the card says so — a dashboard that can only confirm its own thesis is decoration, not evidence. These cards summarise the controlled toy experiment (devlab/alignment_experiment.py, n=3000); panels M1–M4 immediately below now re-ask the same four questions of the real TRELLIS.2 runs, and largely disagree.

M1–M4 · The same questions, on real TRELLIS.2 data loading…

Panels M1–M4 below are computed from real 4B-parameter generation traces (devlab/real_mechanism.py) — no synthetic frustum, no 33.8K-parameter TinyFlow, no new GPU time. They re-ask the toy's four questions of the pipeline that actually ships. Two things to hold onto while reading them: n is far smaller than the toy's 3000 (and differs between panels, because latent telemetry was added partway through this session), and the answers mostly disagree with the toy. That disagreement is the finding, not a defect in either measurement.

M1 · Velocity along the fork's two paths real · v_θ on reference vs delta

The toy version of this panel drew "baseline field vs DPO-aligned field" side by side. That comparison does not exist in the real pipeline — there is one frozen v_θ, and DPO steers the input latent rather than the weights. So the real analogue is the same field's speed measured along the two trajectories the pipeline genuinely explored from each fork: the unperturbed reference continuation, the random perturbation, and the steered result. Velocity is recovered exactly from the sampler's own pred_v, not estimated.

M2 · Path straightness real · does steering straighten the trajectory?

Tortuosity — arc length ÷ straight-line distance, 1.0 being a perfectly straight path — measured on the real latent trajectories through each fork window. Scale-free by construction, which is what makes it poolable across runs whose projection bases differ (see real_mechanism.py); raw curvature is not, and raw 2-D positions from different runs are never overlaid here for the same reason.

M3 · Reward distribution shift real · every scored fork on disk

Real geometric_judge scores for all three candidates at every fork of every real run: the unperturbed reference, the random perturbation, and the gradient-steered result. Densities, so unequal counts cannot fake a shift; dashed lines are means. Differences are paired within each fork (same image, same seed, same branch point) and bootstrapped.

M4 · What the gradient steps actually do real · one line per branch

The differentiable detail proxy over gradient steps, for every real branch that ran any. Each branch is normalised to its own step-0 gap so the shapes are comparable — these runs used branch_noise_scale from 0.02 to 1.0, which changes the raw magnitudes by four orders of magnitude, so a pooled average across them would be a composition artifact rather than a trend.

M5 · The ODE → SDE mapping toy model — not TRELLIS.2

DPO needs a policy with a tractable likelihood ratio; a deterministic ODE has a Dirac path measure and no usable density. The escape is that the ODE is the σ = 0 member of a family of SDEs that all share its time marginals. The table tests exactly that: the same trained field integrated both ways. Per-sample RMSE must be large (different paths) while mean shift ≈ 0 and std ratio ≈ 1 (same distribution). If only the second held, the SDE would have silently collapsed back to the ODE and the whole argument would be circular.

M6 · Reference-free alignment toy model — not TRELLIS.2

The reference-based objective needs a second frozen copy of the flow model and a second backward-enabled forward pass per pair. On this repo's own hardware that is not academic: one such forward through the SLat model retains ~9.5 GB of activations, and four of them per gradient step is what produced the 36.27 GiB MPS OOM that checkpointed_blocks() was written to fix. Dropping the reference removes a whole model from memory. The question is what it costs in quality.

M7 · Provenance & limits what this does and does not show

Every number on this page comes from one reproducible script. What is real and what is a stand-in, stated plainly — including the two claims from the brief that could not be tested here at all.
